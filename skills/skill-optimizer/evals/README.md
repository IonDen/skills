# Evals

`evals.json` holds six prompts with expected outcomes; `fixtures/` holds three SKILL.md files the prompts run against. `lean` is a two-line skill with nothing worth cutting. `release-checklist` is a longer skill with numbered steps, a Rules section, a Troubleshooting section and a closing reminder, and it backs three of the prompts: a full shrink, a request to delete the whole Rules section, and a report-only pass. `vague-description` has a short body but a frontmatter description that runs past the length limit and never says when to use the skill. To run one, copy its fixture into a fresh folder as `SKILL.md` (this is `<SKILL_DIR>`), make an `<OUTPUTS_DIR>` for the report, and record the SHA-256 of every file first. The fixtures are named `SKILL.fixture.md` rather than `SKILL.md` so an installer doesn't mistake them for real skills; the rename to `SKILL.md` only happens in the throwaway copy you run against.

Eval 0 checks that a skill with nothing to cut gets reported as such and left untouched. Eval 1 checks a full shrink: every rule sentence, anchored step and literal has to survive, the frontmatter has to stay untouched, and anything the workflow can't decide on its own (a section proposed for moving, a sentence that reads as motivation but carries a rule word) has to land under a decision heading in the report rather than get applied. Eval 2 asks for a cut the gate has to refuse, deleting the whole Rules section, and checks that the refusal holds and the report offers alternatives that keep the rules. Eval 3 is report-only and checks that nothing changes on disk while the report still proposes cuts, states their gate status, and asks for approval. Eval 4 has no fixture: instead of `<SKILL_DIR>` it hands the workflow a captured `/skill-doctor` report through `<DOCTOR_REPORT>` (produced by running `/skill-doctor` in Claude Code and saving its output to a file), for a general "my skills eat my context" request, and checks that the response triages against real usage data rather than rewriting a skill blind. Eval 5 checks that an over-length description gets flagged with a suggested rewrite and left alone.

To run one by hand: copy the fixture into a fresh folder as `SKILL.md`, give a fresh agent the skill and the prompt with its placeholders filled, then check the expected outcome against the resulting files and the report. Wherever a run produces `requirements.md` and `frozen.json`, re-run `verify_rewrite.py` against them yourself and confirm it agrees with the gate status the report states.

Recorded runs (2026-09-24, skill 1.0.0, a fresh Claude Sonnet agent per run, one run per eval; evidence under [`recorded/2026-09-24-evals/`](recorded/2026-09-24-evals/)): all six passed. Eval 0 left `SKILL.md` byte-identical, and the gate re-run reported `unchanged` (91 to 91 characters) with a report explaining that both sentences are instructions. Eval 1 shrank the body from 2,898 to 1,851 characters (-36.1%, 89 to 66 lines) with the frontmatter byte-identical, a `pass` on the gate re-run, every rule sentence and literal intact (the closing reminder still last), all five numbered steps anchored across 21 requirements, the motivation and definition sections cut with stated reasons, and the rule-word motivation sentence together with a proposed Troubleshooting move both held back under the decision heading instead of applied; reverse reconstruction recovered all 21 requirements. Eval 2 left `SKILL.md` byte-identical: the requested candidate was rejected on re-run for lost rules and lost literals, and the report named the rules and offered three alternatives that keep them. Eval 3 left every file byte-identical while proposing a shrink from 2,898 to 1,380 characters (-52.4%) that the gate re-run marked as needing confirmation for a Troubleshooting move, with the report asking for approval; its reverse reconstruction step caught a dangling reference left by collapsing an option menu down to its default line. Eval 4 read a real `/skill-doctor` capture, named the skills it showed as never invoked and where to turn them off, recommended disabling rather than rewriting, changed nothing, and asked which skill to optimize. Eval 5 left the frontmatter byte-identical, shrank the body from 435 to 151 characters (-65.3%) with a `pass` on the gate re-run, kept the rule sentence ("Do not edit released entries") and the `CHANGELOG.md` literal it names, and flagged the description as 1,030 characters, six over the limit, with no statement of when to use the skill, proposing a shorter description without applying it.

Two baseline runs used the same fixtures and prompts with no skill available, for comparison against evals 1 and 2. Asked to shrink the release-checklist skill by judgment, a baseline agent cut the body by 28% but reworded the option-menu paragraph, deleted a rule-word motivation sentence without asking, reworded a rule to drop its exception clause, and moved the closing reminder away from the end: a candidate the gate would reject, and the agent never produced a requirement list, a freeze, or a reverse reconstruction. Asked to delete the whole Rules section, a second baseline agent did exactly that, losing four rules (the ban on committing to `main`, the tag-push rule with its exception, the pytest requirement, and the 20 GiB limit) with nothing flagged.

In evals 1 and 2 the agent wrote its own approval file mid-run: in eval 1 only to preview a variant it never applied, and in eval 2 reading "delete the whole Rules section" as approval for those specific rule sentences, though the gate still rejected the candidate on the anchors and literals it lost. The workflow now says that only the user's answer to a listed sentence counts as approval, and that the file is never written before asking. Eval 3's reverse reconstruction step also found a real gap in the workflow's guidance: collapsing an option menu down to just its default sentence can leave an earlier reference to "any of these" pointing at nothing. The option-menu guidance in `references/what-not-to-cut.md` now calls that out directly.
