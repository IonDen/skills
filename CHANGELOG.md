# Changelog

## 2026-09-24 (skill-optimizer 1.0.2)

- `skill-optimizer` rejected an unchanged skill whose table had a number with a bound at the end of one row and a word at the start of the next, such as `≤ 0.20` followed by `Pixel mismatch ratio`. The freeze scanned the whole body as one text, so it recorded `≤ 0.20 Pixel` as a literal, which the file never contains. It now scans each table cell, list item and paragraph on its own as well, and keeps a match from the whole-text scan only when the file holds it as written. So `≤ 0.20` is protected on its own, while a bound whose unit starts the next paragraph (`under 20`, then `GiB`) stays protected as `under 20 GiB`. Over 23 skills, every literal 1.0.1 recorded correctly is still recorded. A test also checks that each literal the freeze records in a skill shipped here is found again in that skill's own text. The version goes to 1.0.2 and the plugin to 0.4.1.

## 2026-09-24 (subagent-optimizer 1.4.0)

- `subagent-optimizer` now looks at reasoning effort as well as the model. Claude Code subagents accept an `effort` field (`low` to `max`) that overrides the session's level, and until now the skill ignored it. The scanner prints each agent's effort next to its model, in both the readable and the JSON output, and raises four flags: `EFFORT_INHERIT` when the field is missing and the agent runs at whatever the session uses, `EFFORT_UNSUPPORTED` when it is set on `haiku`, which is not on Claude Code's list of models that take effort, `EFFORT_INVALID` for a value outside the five documented levels, and `HIGH_EFFORT_READONLY` when an agent that cannot edit files or run shell commands is set to `xhigh` or `max`. The skill recommends model and effort together from the agent's job (`haiku` with no effort, or low or medium on a larger model, for read-only search workers; medium for implementation; high for planners, architects and security reviewers; the top two levels only when the user confirms the work needs them) and, like model changes, presents a new level as a candidate to test on the agent's real task. The references quote Claude Code's per-model level table. The description now says the skill is for agent definitions (`.claude/agents/` and `.codex/agents/`) and that agent skills belong to `skill-optimizer`, so the two stop competing for the same requests. The top heading reads "Subagent optimizer" after the rename, the Codex display name is "Subagent Optimizer", the README's version history covers 1.3.0 to 1.4.0, and a fifth eval checks a read-only agent at `effort: max`.
- `subagent-optimizer` also audits Codex custom agents, the `.toml` files under `~/.codex/agents/` and a project's `.codex/agents/`, which the scanner now finds by default. They share the size and duplicate-block checks with Claude agents but get none of the tool flags, because Codex has no per-agent tool list. Seven new flags cover what goes wrong when people port a Claude agent or pin a model: a missing `name`, `description` or `developer_instructions`; a Claude key such as `tools` or `effort`, which makes Codex skip the whole agent; keys such as `sandbox_mode` and `mcp_servers` that current Codex parses but does not apply to a custom agent; an effort outside Codex's six levels or one the pinned model does not offer (`ultra` on `gpt-6-luna`, for example); a model retired or deprecated for ChatGPT sign-in; and a `model` pinned without `model_reasoning_effort`. The model and effort tables are dated 2026-09-24 and sit in one block of the scanner, so they are easy to refresh. The skill recommends `model` and `model_reasoning_effort` together from the Codex docs' starting points, never maps effort names across tools, and suggests `[agents]` defaults for a whole fleet. It edits Codex files line by line and never adds a key Codex does not know, so `bump_version.py` refuses `.toml` files. Reading `.toml` needs Python 3.11 or later; on 3.10 the scanner lists Codex files as not scanned and carries on with the Claude ones. A sixth eval checks a Codex agent that copied Claude keys.
- More Codex flags. `CODEX_CLAUDE_MODEL` catches a `model` Codex cannot resolve because it is a Claude value (`sonnet`, `opus`, `haiku`, `fable`, `inherit` or a `claude-` ID); the agent still loads but its requests fail, and a `claude-` ID is medium rather than high when a `model_provider` is set. `CODEX_SUFFIX_CASE` catches a file such as `Agent.TOML` that Codex will not load from an agents folder. `CODEX_UNKNOWN_KEY` (high) catches a top-level key such as `prompt` or `version` that is neither a Codex key nor a Claude one, which makes Codex skip the agent. The list of known keys comes from the Codex source at rust-v0.156.1 and sits in the dated block with the other tables. The scanner also reads roles declared as `[agents.<name>]` tables in `$CODEX_HOME/config.toml` and `./.codex/config.toml` and scans their `config_file` wherever it lives; a declared role is reported under its table key, may take its description from the table, and is never renamed. `CODEX_HOME` now moves the default Codex agents folder too. Keys such as `sandbox_mode`, `approval_policy` and `mcp_servers` are reported at low severity as inert on Codex 0.149 and later, and kept, because older Codex still applies them; `hooks` and `service_tier` join that list (Codex copies `service_tier` from the file, then replaces it with the parent's tier when it spawns the agent). Duplicate blocks are matched by file rather than by name, so a Claude agent and its Codex port with the same name are no longer merged. Files that cannot be read or parsed, files over 1 MiB and symlinks (as arguments or in a walk, `.md` or `.toml`; the scanner does not follow them, though Codex does) are listed as not scanned and the scan goes on. A walk skips `config.toml`, which is read only for declared roles. The Haiku effort flag is now a note: the pinned model does not support effort, but a per-invocation model override can still change the model.
- The plugin version goes to 0.4.0.

## 2026-09-24 (skill-optimizer 1.0.1)

- `skill-optimizer` rejected an unchanged skill whenever it mentioned a version, date or number inside a longer name, such as `rust-v0.156.1` or `python-3.12`. The freeze recorded `v0.156.1` on its own, while the gate only counts a literal as present when it is not glued to a longer word, so the literal always looked lost. The freeze now records the whole name, which the gate finds, and a changed version inside it is still caught. The version goes to 1.0.1 and the plugin to 0.3.1.

## 2026-09-24 (subagent-optimizer 1.3.1)

- Two sentences in `subagent-optimizer`'s SKILL.md only repeated what the surrounding text already says ("A tight allowlist is cheaper and more correct." and "The scan tells you what is off; you decide the fix.") and are gone. `skill-optimizer` (#9) found them and checked that every rule and instruction it tracks survived; the skill's own evals 1 and 3 gave the same results before and after. The version goes to 1.3.1.

## 2026-09-24

- Add `skill-optimizer` 1.0.0: cuts a skill's token cost without losing an instruction. It freezes every rule, anchor, literal and code block in the original `SKILL.md` before any rewrite exists, then gates the candidate deterministically: a rule sentence, an anchored sentence, a literal, or the position of a strong rule or a rule heading can't disappear or move without the gate rejecting the candidate outright or flagging it. A rule that lands under a different heading or only in `references/` goes back where it was unless you already approved that move, the work copy never includes a link other than the skill's own, and a rule sentence can be deleted only whole and only with a human sign-off; a trimmed rule is still rejected. The skill runs through to its report without stopping for questions: when it is unsure a cut is safe, it keeps the text and lists the cut as optional, with what it would save. It shows `/skill-doctor` usage data as information and never recommends disabling or deleting a skill. It handles agent skills only; subagent definitions stay with `subagent-optimizer`. What passes the gate is not itself a claim that behaviour is unchanged: catching that needs a reverse-reconstruction read and, where the skill ships evals, a same-prompt run against both versions, and the report has to state whether that step ran or was skipped and why. Run against a copy of this repository's own `subagent-optimizer`, it cut the body from 8,863 to 8,758 characters (-1.2%), left two rule-carrying sentences as flagged decisions instead of removing them, and two of `subagent-optimizer`'s four evals (1 and 3) came back with the same 13 of 13 expected clauses met on the optimized copy as on the original. The skill was already tight, and the optimizer said so instead of forcing a bigger number.

## 2026-09-20 (rename)

- The skill is now `subagent-optimizer`, was `agent-optimiser`, and the version goes to 1.3.0. Searching the skills directory showed the old name was findable only by people who already knew it: it surfaced for "optimiser" and for nothing else, while "subagent", "optimizer", "claude code subagents" and "audit agents" all returned other authors' skills. Names weigh far more than descriptions in that ranking, and the American spelling is what most people type. Install it as `npx skills add IonDen/skills --skill subagent-optimizer`; the old name is gone rather than aliased, because two installs were not worth a permanent second identity.

## 2026-09-20 (harness safety)

- Hardened `evals/measure/measure.sh` after a Socket audit on skills.sh flagged it. It validated nothing, so a crafted label could write outside the output directory; it passed `--dangerously-skip-permissions`; and a shell expansion sat inside a quoted heredoc, so the summary path never resolved and the script failed at its last step. It now validates the label and both paths, uses the `acceptEdits` permission mode, passes the output directory to Python as an argument, and documents that it runs an agent against a throwaway copy. Five tests cover the guards.

## 2026-09-19

A controlled probe on Claude Code 2.1.278 puts a no-`tools`-field subagent at 18,437 input tokens on Haiku 4.5 and 31,882 on Sonnet 5, against 10,241 and 13,401 with a three-tool allowlist.
