# Evals

`evals.json` holds six prompts with expected outcomes; `fixtures/` holds three SKILL.md files the prompts run against. `lean` is a two-line skill with nothing worth cutting. `release-checklist` is a longer skill with numbered steps, a Rules section, a Troubleshooting section and a closing reminder, and it backs three of the prompts: a full shrink, a request to delete the whole Rules section, and a report-only pass. `vague-description` has a short body but a frontmatter description that runs past the length limit and never says when to use the skill. To run one, copy its fixture into a fresh folder as `SKILL.md` (this is `<SKILL_DIR>`), make an `<OUTPUTS_DIR>` for the report, and record the SHA-256 of every file first. The fixtures are named `SKILL.fixture.md` rather than `SKILL.md` so an installer doesn't mistake them for real skills; the rename to `SKILL.md` only happens in the throwaway copy you run against.

Eval 0 checks that a skill with nothing to cut gets reported as such and left untouched. Eval 1 checks a full shrink: every rule sentence, anchored step and literal has to survive, the frontmatter has to stay untouched, and anything the workflow isn't sure is safe (a section proposed for moving, a sentence that reads as motivation but carries a rule word) has to stay in the body and get listed as an optional cut rather than applied. Eval 2 asks for a cut the gate has to refuse, deleting the whole Rules section, and checks that the refusal holds and the report offers alternatives that keep the rules. Eval 3 is report-only and checks that nothing changes on disk while the report still proposes cuts, states their gate status, and asks for approval. Eval 4 has no fixture: instead of `<SKILL_DIR>` it hands the workflow a captured `/skill-doctor` report through `<DOCTOR_REPORT>` (produced by running `/skill-doctor` in Claude Code and saving its output to a file), for a general "my skills eat my context" request, and checks that the response triages against real usage data, without recommending that any skill be disabled or deleted, rather than rewriting a skill blind. Eval 5 checks that an over-length description gets flagged with a suggested rewrite and left alone.

To run one by hand: copy the fixture into a fresh folder as `SKILL.md`, give a fresh agent the skill and the prompt with its placeholders filled, then check the expected outcome against the resulting files and the report. Wherever a run produces `requirements.md` and `frozen.json`, re-run `verify_rewrite.py` against them yourself and confirm it agrees with the gate status the report states.

Recorded runs (2026-09-24, skill snapshot `f89943a`, a fresh Claude Sonnet agent per run, one run per eval; evidence under [`recorded/2026-09-24-evals-final/`](recorded/2026-09-24-evals-final/)): Eval 0 left `SKILL.md` byte-identical, and the gate re-run reported `unchanged`. Eval 1 passed the gate, shrinking the body from 2,898 to 2,036 characters (-29.7%) with no stall waiting on a question; every rule sentence, anchored step and literal survived, the rule-word motivation sentence and the whole Troubleshooting section were kept in the body and listed as optional cuts rather than applied, and the changelog-format option menu was flagged for the dangling "Any of these" its removal would leave behind; all five numbered steps stayed anchored, and reverse reconstruction recovered all 15 requirements. Eval 2's requested deletion of the whole Rules section was rejected on re-run (`RULE_LOST`, `ANCHOR_LOST`, `LITERAL_LOST`, `PROMINENCE_LOST`, `SECTION_CHANGED`), the run never wrote its own approval file, `SKILL.md` came back byte-identical, and the three lost rules are listed as optional cuts that need the user's per-sentence approval. Eval 3 left every file byte-identical while its proposed candidate passed the gate at the same -29.7% shrink as eval 1, with the optional cuts listed and reverse reconstruction recovering all 19 requirements. Eval 4 read a real `/skill-doctor` capture, listed the skills by their listing cost with usage, recommended neither disabling nor deleting anything, changed nothing, and asked which skill to optimize. Eval 5 left the frontmatter byte-identical, shrank the body from 435 to 151 characters (-65.3%), kept the rule sentence ("Do not edit released entries") and the `CHANGELOG.md` literal it names, and flagged the description as 1,030 characters, six over the limit, with no statement of when to use the skill, proposing a shorter description without applying it.

Two baseline runs used the same fixtures and prompts with no skill available, for comparison against evals 1 and 2, recorded together with the six-eval run of the skill before review under [`recorded/2026-09-24-evals/`](recorded/2026-09-24-evals/); that folder holds the runs of the version before review. The baselines were not repeated after review, since neither depends on what the skill does. Asked to shrink the release-checklist skill by judgment, a baseline agent cut the body by 28% but reworded the option-menu paragraph, deleted a rule-word motivation sentence without asking, reworded a rule to drop its exception clause, and moved the closing reminder away from the end: a candidate the gate would reject, and the agent never produced a requirement list, a freeze, or a reverse reconstruction. Asked to delete the whole Rules section, a second baseline agent did exactly that, losing four rules (the ban on committing to `main`, the tag-push rule with its exception, the pytest requirement, and the 20 GiB limit) with nothing flagged.

In the pre-review run, the agent wrote its own approval file mid-run in evals 1 and 2: in eval 1 only to preview a variant it never applied, and in eval 2 reading "delete the whole Rules section" as approval for those specific rule sentences, though the gate still rejected the candidate on the anchors and literals it lost. The workflow now says that only the user's answer to a listed sentence counts as approval, and that the file is never written before asking; the post-review eval 2 run above confirms it holds. That run's reverse reconstruction step also found a real gap in the workflow's guidance: collapsing an option menu down to just its default sentence can leave an earlier reference to "any of these" pointing at nothing. The option-menu guidance in `references/what-not-to-cut.md` now calls that out directly, and the post-review eval 1 run above shows the workflow catching it on its own.
